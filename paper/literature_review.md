# Energy Footprint of LLM-Generated Code vs. Human-Written Code

## Literature Review and Research Background

---

## I. Introduction

The proliferation of large language models (LLMs) capable of generating source code has fundamentally altered software development workflows. Tools such as GitHub Copilot, ChatGPT, Claude, and Gemini are now routinely used by developers to produce code across a wide range of programming tasks. Industry surveys indicate that a substantial and growing fraction of production code is now partially or fully generated by LLMs [1]. While considerable research effort has been devoted to evaluating the *functional correctness* of LLM-generated code, a critical dimension remains largely unexplored: the *energy efficiency and runtime performance* of such code compared to human-written alternatives.

This gap is significant for two reasons. First, the global ICT sector accounts for an estimated 2–4% of worldwide greenhouse gas emissions, with software execution contributing meaningfully to this footprint [2]. The Green Software Foundation and related initiatives have emphasized that software design choices — including algorithmic selection, data structure usage, and implementation patterns — materially affect energy consumption at scale [3]. Second, LLM-generated code is increasingly deployed in production systems where it executes millions or billions of times, meaning that even small per-invocation inefficiencies can compound into substantial energy costs over the lifetime of a deployment.

This paper presents, to the best of our knowledge, the first systematic empirical study comparing the energy consumption of LLM-generated code against human-written code across multiple task categories, languages, and complexity levels. We aim to bridge the gap between the well-studied domain of LLM code correctness and the emerging field of green software engineering.

## II. Related Work

### A. Green Software Engineering and Software Energy Consumption

The concept of *green software engineering* encompasses practices aimed at reducing the environmental impact of software systems throughout their lifecycle. Calero and Piattini [4] introduced a comprehensive framework for sustainable software, identifying energy consumption during execution as a primary contributor to software's carbon footprint. The Green Software Foundation formalized the *Software Carbon Intensity (SCI)* specification, which quantifies carbon emissions attributable to a software system as a function of energy consumption, hardware efficiency, and grid carbon intensity [3].

Empirical research on software energy consumption has established that implementation choices at the code level can produce order-of-magnitude differences in energy use. Pereira et al. [5] conducted a landmark study comparing 27 programming languages across 10 benchmark problems, finding that energy consumption varied by up to 80× between languages for equivalent tasks. Their work demonstrated that execution time, while correlated with energy consumption, is not a reliable sole proxy — memory usage patterns and CPU utilization profiles also contribute independently.

Georgiou et al. [6] examined how software design patterns affect energy consumption in object-oriented programs, finding that certain patterns (e.g., decorator, observer) impose measurable energy overhead. Similarly, Hasan et al. [7] showed that seemingly minor refactoring decisions — such as loop unrolling, collection type selection, and string concatenation strategy — can produce statistically significant differences in energy consumption in Java applications.

At the algorithmic level, Bunse [8] demonstrated that the choice of sorting algorithm affects energy consumption in ways that do not strictly follow time-complexity expectations, as cache behavior and memory access patterns introduce additional energy costs not captured by Big-O analysis. This finding is particularly relevant to our study, as LLMs may select algorithms based on frequency in training data rather than energy optimality.

### B. Tools and Methodologies for Software Energy Measurement

Several measurement approaches and tools have been developed for quantifying software energy consumption:

**Hardware-based measurement.** Direct power measurement using external power meters (e.g., Watts Up? Pro, Yokogawa) attached to the system's power supply provides ground-truth energy readings. While highly accurate, this approach is expensive, requires physical access, and cannot isolate individual process contributions on multi-tenant systems [9].

**Intel RAPL (Running Average Power Limit).** Modern Intel processors expose energy counters through the RAPL interface, providing per-package and per-core energy readings at high temporal resolution. RAPL has been validated against external power meters and shown to be accurate within 5–10% for CPU-bound workloads [10]. Tools such as `perf`, `likwid`, and `powertop` provide user-space access to RAPL counters. Khan et al. [11] provided a comprehensive evaluation of RAPL's accuracy across workload types, noting reduced accuracy for memory-intensive workloads.

**Software estimation tools.** CodeCarbon [12] estimates energy consumption by combining CPU utilization data with hardware TDP (Thermal Design Power) specifications and regional carbon intensity data. While less precise than RAPL, it offers portability across platforms and integrates easily into Python workflows. Similarly, Scaphandre [13] provides process-level power estimation on Linux systems.

**Proxy metrics.** In environments where direct energy measurement is infeasible, execution time and peak memory consumption serve as established proxies. Pereira et al. [5] found a Spearman correlation coefficient of ρ = 0.77 between execution time and energy consumption across their language benchmark, while memory usage showed ρ = 0.59. These proxy metrics, while imperfect, enable energy-awareness research in cloud and virtualized environments where hardware counters may be unavailable.

For the present study, we adopt a multi-metric approach combining execution time (wall-clock and CPU time), peak memory consumption, and — where available — RAPL-based energy readings, supplemented by software complexity metrics.

### C. LLM Code Generation: Correctness and Quality Benchmarks

The evaluation of LLM-generated code has been a highly active research area since the introduction of Codex [14] and subsequent models.

**Functional correctness benchmarks.** Chen et al. [14] introduced HumanEval, a benchmark of 164 hand-crafted Python programming problems with unit test suites, and proposed the pass@k metric to evaluate functional correctness. Austin et al. [15] introduced the Mostly Basic Programming Problems (MBPP) benchmark comprising 974 crowd-sourced Python tasks. Li et al. [16] extended evaluation to competitive programming with the CodeContests benchmark drawn from Codeforces problems. More recently, Liu et al. [17] introduced EvalPlus, which augmented HumanEval and MBPP with substantially more test cases (80× increase) to reduce false positive rates.

**Security and vulnerability analysis.** Pearce et al. [18] conducted an early study of security weaknesses in Copilot-generated code, finding that approximately 40% of generated programs in security-sensitive scenarios contained vulnerabilities corresponding to CWE categories. Tony et al. [19] performed a broader analysis and found that LLM-generated code exhibits vulnerability patterns similar to those found in human-written open-source code, though at moderately higher rates for certain CWE categories.

**Code quality and maintainability.** Siddiq et al. [20] evaluated the quality of LLM-generated code using static analysis metrics including cyclomatic complexity, cognitive complexity, and code duplication, finding that LLM-generated code tends to be more verbose and exhibits higher cyclomatic complexity than expert human solutions. Fan et al. [21] examined code smells in LLM-generated code and found elevated rates of long methods, large classes, and duplicated logic compared to human-written baselines.

**Performance-adjacent studies.** Closest to our work, a small number of studies have touched on the runtime characteristics of LLM-generated code without making energy consumption a primary focus. Huang et al. [22*] compared the execution efficiency of code generated by several LLMs on competitive programming tasks, finding that LLM-generated solutions tended to use 1.2–2.5× more execution time than top-ranked human solutions. Liu et al. [23*] briefly noted performance differences in an appendix to a correctness study but did not conduct systematic energy analysis. *(Citations marked with * indicate papers whose exact publication status could not be verified and should be confirmed by the authors.)*

### D. The Research Gap: Energy Efficiency of LLM-Generated Code

Despite the extensive body of work on both software energy consumption and LLM code generation quality, these two research streams have remained largely disconnected. Our systematic search of IEEE Xplore, ACM Digital Library, and Google Scholar (conducted through early 2025) identified no peer-reviewed study that:

1. Systematically measures energy consumption (or validated proxies thereof) of LLM-generated code across multiple task categories;
2. Compares these measurements against both expert-optimized and typical human-written baselines;
3. Analyzes the relationship between code complexity metrics and energy consumption specifically for LLM-generated code;
4. Evaluates whether the energy gap varies by task domain (e.g., numerical computation vs. string processing vs. data transformation).

This gap is noteworthy because several characteristics of LLM-generated code suggest it may exhibit systematically different energy profiles compared to human-written code:

- **Algorithm selection bias.** LLMs generate code that reflects the distribution of their training data. Common but suboptimal patterns (e.g., bubble sort, repeated string concatenation, nested linear searches) may be over-represented relative to what an experienced developer would choose [20].
- **Verbosity and redundant computation.** LLM-generated code frequently includes unnecessary intermediate variables, redundant type conversions, and defensive checks that add computational overhead [21].
- **Suboptimal data structure choice.** LLMs may default to general-purpose data structures (e.g., lists instead of sets for membership testing, dictionaries instead of arrays for sequential access) when more efficient alternatives exist for the specific use case.
- **Lack of performance intent.** Human developers optimizing for performance apply domain knowledge, profiling feedback, and platform-specific optimizations that LLMs cannot replicate without explicit prompting.

Conversely, LLM-generated code may in some cases exhibit *lower* energy consumption if it leverages well-optimized standard library functions rather than implementing algorithms from scratch, or if it produces more regular memory access patterns amenable to hardware optimization.

These competing hypotheses motivate the empirical investigation presented in this paper.

## III. Research Questions

Based on the identified research gap, we formulate the following research questions:

**RQ1: Is there a statistically significant difference in energy consumption between LLM-generated and human-written code for equivalent programming tasks?**

This question addresses the fundamental premise of the study. We test the null hypothesis that LLM-generated and human-written code exhibit no significant difference in energy-related metrics (execution time, memory usage, and energy proxy estimates) using paired statistical tests with appropriate corrections for multiple comparisons.

**RQ2: Does the energy gap vary across programming task categories?**

We hypothesize that the magnitude and direction of any energy difference between LLM-generated and human-written code may depend on the nature of the task. We categorize benchmark tasks into four domains: (a) sorting and searching, (b) string processing, (c) numerical computation, and (d) data transformation/aggregation. We analyze whether the energy differential is consistent across categories or whether LLMs exhibit domain-specific strengths and weaknesses.

**RQ3: Does code complexity correlate with energy consumption differences?**

We examine whether static code complexity metrics — specifically cyclomatic complexity, lines of code (LOC), and Halstead complexity measures — are predictive of energy consumption differences between LLM-generated and human-written solutions. A positive finding would suggest that complexity metrics could serve as lightweight, pre-execution indicators of energy inefficiency in LLM-generated code, enabling automated screening in CI/CD pipelines.
